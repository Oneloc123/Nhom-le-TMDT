# PrintKraft hybrid chatbot (Gemini)

## Current design

The existing floating JSP widget and `/api/chatbot/message` endpoint are retained.
The endpoint continues to use the existing session-scoped request cache, request limit,
CSRF validation in `AuthFilter`, and FAQ fallback.

The hybrid flow is:

1. `ChatbotMessageServlet` reads the current user from the existing authenticated session.
2. `ChatbotDataService` performs read-only queries through the existing `ProductDao`
   and `OrderDao`. Order queries are always scoped by the current user's ID.
3. `GeminiChatClient` sends the question and the backend facts to Gemini.
4. Gemini writes a Vietnamese response. It does not receive database credentials, SQL access,
   or tools capable of changing orders or tickets.
5. If Gemini is not configured or its API is unavailable, the current deterministic FAQ service
   responds instead.

Support escalation remains the existing `/support` flow. The chatbot only links to that page;
it does not create, reply to, reopen, rate, or close support tickets.

## Configure Gemini

Create an API key in Google AI Studio and configure environment variables for the Tomcat process:

- `GEMINI_API_KEY`: required secret. Keep it on the server; never put it in JSP or JavaScript.
- `GEMINI_MODEL`: optional model override. Default: `gemini-3.8-flash`.

Example in PowerShell before starting Tomcat from the same terminal:

```powershell
$env:GEMINI_API_KEY = "YOUR_GEMINI_API_KEY"
$env:GEMINI_MODEL = "gemini-3.8-flash"
```

If Tomcat is started by IntelliJ, add these variables to the Tomcat Run/Debug Configuration
environment variables. Restart Tomcat after changing them.

If `GEMINI_API_KEY` is absent, the widget remains usable with the deterministic FAQ fallback.
No API key is committed to this repository.

## Endpoints and data boundaries

- Chat API: `POST /api/chatbot/message` (existing endpoint).
- Product facts: active, approved catalog entries and active shop offers from `ProductDao`.
- Order facts: only the authenticated user's orders from `OrderDao.findByCodeForUser`
  or `OrderDao.listByUser`.
- Support: link to `/support`; existing ticket workflow is unchanged.
- FAQ: existing deterministic intent/FAQ rules in `ChatbotService.answerFaq`.

The order code format currently generated by the application is `PK-########-######`.
When a customer asks about an order without specifying a code, the chatbot context includes
up to five recent orders belonging to that authenticated customer.

## Test checklist

1. Without `GEMINI_API_KEY`, open the widget and verify FAQ fallback works.
2. With a valid key, ask a general FAQ question and verify a Vietnamese answer.
3. Ask for products by name/material and verify only catalog results are described.
4. Ask for products generally and verify the response does not invent prices or stock.
5. While logged in, ask for recent orders and verify only that account's orders appear.
6. While logged in, ask for another account's order code and verify it is not found.
7. Ask about orders while logged out and verify the bot asks the visitor to sign in.
8. Ask for a human, refund, complaint, or product issue and verify the link opens `/support`.
9. Verify an invalid CSRF token is rejected by the existing `AuthFilter`.
10. Temporarily use an invalid Gemini key and verify the FAQ fallback remains available.

## Notes

The implementation intentionally does not add chat-history tables or alter the database schema.
Conversation/request handling remains session-scoped as in the existing chatbot. Gemini calls use
the REST Interactions API with `store=false` and the API key is sent in the `x-goog-api-key` header.
See the [Gemini Interactions API documentation](https://ai.google.dev/gemini-api/docs/get-started).
